# The Legend of Zelda: Ocarina of Time

The Switch 2 base dump reaches its title screen on the Mac. VideoToolbox decodes the 1920×1080 AV1 track. The movie library runs its NDVE compute shaders to produce the background behind the logo and menu. Gameplay validation is open.

## Profile

SDK 22.2.8, NVN API 231.40, with Nintendo's sead, agl and gsys. The three loaded modules are `main`, `subsdk0` (NintendoSDK_movie), and `sdk`. The NPDM declares 48 MiB of system resources. Startup requests a 6.20 GiB heap, which fits in the profile's 12 GiB reservation with the stack and alias regions. The registered builds are the supplied base dump (`v0`) and update `v131072` (1.1.1), which a NUP carries alone as the whole game: their three modules are the same builds, and v131072's shader split is v0's key for key, so the tables are v131072's (`package`, `shader_versions`).

## Mac dry run

Use the rewritten `patched_v0` and the original extracted `base/romfs`. Build the host with `make -C dm/host GAME=0400486024DEC000` and use the [Mac shader build](../../../docs/development.md#build-by-hand-mac). From the repository, set `DUMP` to the folder containing `base` and `WORK` to the build and run workspace beside it.

```sh
mkdir -p "$WORK/run/save" "$WORK/run/temp" "$WORK/font"
python3 dm/tools/make_ext_font.py "$WORK/font/nintendo_ext.ttf"
DM_ROOT="$WORK" DM_ROMFS="$DUMP/base/romfs" DM_SAVE="$WORK/run/save" \
  DM_TEMP="$WORK/run/temp" DM_MSL_DIR="$WORK/shader/cache" DM_FONT_DIR="$WORK/font" \
  DM_NVN_SHMAP="$PWD/dm/games/0400486024DEC000/shader_map.tsv" \
  DM_WINDOW=1 DM_METAL_HUD=1 DM_FOCUS_KEEP=1 DM_AUDIO=1 \
  dm/host/dmhost "$WORK/patched_v0"
```

`DM_FOCUS_KEEP=1` lets the title keep playing while another app has focus. The profile prewarms the 11 NDVE compute pipelines used by the title. On the Apple M5 that took 17.7 s on a cold run, with a progress screen, and 7 ms with the archive warm. Compiling the same pipelines during the first submission had blocked the first movie frame for tens of seconds. The larger scene shader set also triggers a separate graphics-pipeline prebuild. On the first run with that set, the startup screen took 86.9 s to hand out all pairs, and the remaining workers finished after 110.6 s total.

Start a new game to reproduce the opening scene transition. With the test save and title flow, `DM_KEYS=f2600:A,f2950:A` advances the menu automatically. `DM_NVN_SHDUMP` saves control sections and code for missing keys to the directory it names.

For a run past the opening, copy the committed save folder to the new run's `DM_SAVE` and load slot 00 from the menu. The checkpoint contains both `slot_00/progress.sav` and `slot_00/caption.sav`. The load screen identifies it as **Kokiri Forest Autosave**. A windowed reload reached the playable scene with the HUD and controls, so rendering can be tested without replaying the movie.

## Upscaler and resolution (current: static analysis of v131072's main, then headless runs from the autosave in Link's house)

- **The upscaler is agl's NDSR network, not FSR.** gsys's `Main.gsys__ModelSceneConfigParam.bgyml` sets `CreateNdsr` (the UI scene's does not) and `CreateFilterAa` (SMAA / FXAA); it has no `CreateDlss` key. `main` holds no FSR, EASU or RCAS string. agl's NDSR parameters (`aglndsr`, `main+0xcd8c50`): `enable`, `view_enable_mask`, `upscale_ratio` 1.0, `two_step_upscale_ratio_threshold` 4.0, `vr_upscale_ratio` 2.0, `vr_enable_dithering`, `vr_sharpening_amount`. NDSR's loader (`main+0xf51360`) opens three packs from `Lib/agl/agl_resource.Nin_Ounce_NVN2.release.sarc.zs`: `agl_ndsr.pck`, `agl_ndsr_vr.pck` and `agl_ndsr_vr_light.pck`, 56 compute keys in all.
- **Colour, read as the host reads it (`up_mfx_color`):** `agl_ndsr.pck` (header +4 `0x10100`) has 11 pairs, one with no curve (encoded in and out, for an 8-bit image) and one with a half-float decode (linear out), Star Fox's shapes (its `3fe6b091bb8c40ce` is here too). In the two `vr` packs the networks come in threes, as Bananza's do: one with a float encode and no decode (linear in, encoded out), a shape MetalFX does not draw yet, and two with no curve at all, which the host takes for encoded colour and draws only into an 8-bit image (into a float image they would be linear). Three small kernels in each (`f8965bffbdf51d78`, `ddc1143b7932a93e`, `3426ccfe7d691d0f` / `a335c1db6270c355`) look like helpers. In a run the game uses `agl_ndsr_vr_light.pck`: docked, the helpers `f8965bffbdf51d78` and `a335c1db6270c355` write the square roots of the scene's colour, and a network of the pack (`fa3033d05c0a41d6` at 1920x1080, `04135bb812a0d66e`, `aad7ea7e5c02f41d`, `d99fbeeb53d38847` at the other sizes) takes the 1920x1080 RGB9E5 scene to the 2560x1440 R11G11B10F output, which is the window's size (one resample; `present: picture shape 2560x1440`). MetalFX draws it ([An upscaler fed square-root colour](../../../docs/reference/rendering.md#an-upscaler-fed-square-root-colour)); taken as linear it washed the picture out.
- **Resolution:** `ModelSceneExtensionParam` (`Pack/Bootup`) gives the final image and base size per mode, 2560x1440 twice and 1920x1080 once, and a dynamic-resolution palette for each: 10 levels at 2560x1440 (`ResolutionReduceScale` 0.75 down to 0.3333, so upscale rates 1.33 to 3.0, load threshold 95) and 8 at 1920x1080 (0.75 to 0.4445, threshold 108). The scene never renders at the output size, so the network always runs. `main` queries no display size (no `oe::GetDefaultDisplayResolution` or `vi::QueryDisplayBufferMaxResolution`), and it imports `oe::GetCurrentGraphicsScale`, HDR status and 120 Hz / VRR queries.
- **Motion and camera:** `EnableMotionBuffer` and `MotionVectors3D` are off and there is no TAA, so MetalFX needs camera-only motion vectors from depth, as on [Donkey Kong Bananza](../040074A01BF12000/README.md#metalfx-temporal-scaling-and-frame-interpolation-current-opt-in-not-played-yet). agl's shaders name gsys's Context members (`cGSysCtxView`, `cGSysCtxProj`, `cGSysCtxViewProj`, `cGSysCtxInvView`, `cGSysCtxNearFarParam`, `cGSysCtxFovyParam`), and Bananza's `camera_mats` (`vertex 0 0x0 0x30`) holds (current, checked in a run with `DM_MFX_PROBE`): the opening's 3D cutscenes and Link's house give a GL perspective camera, 50 degrees, 16:9, near 0.1, far 25037, no projection offset (no jitter), in the 1920x1080 D32F depth pass that has the upscaler's input size; over 15,000 upscaler frames every one had motion vectors, one of them without a camera, and the cutscenes' cuts reset the history.

### Render resolution (current, in a run)

**Render resolution** (`DM_UPSCALE_RATIO`, [`setting_patches.tsv`](setting_patches.tsv)) fixes the scale the game renders at. The dynamic-resolution controller (built at stage start by `main+0x31c3b30` from the palette's level entries: {scale, priority} nodes) returns the chosen level's scale from its update (`main+0x805aa0`) through `main+0x805ff0` (`fmov w9,s8`), and its caller (`main+0x31d3ee0`) makes it the scene's scale when the level changes or the stage starts. One word there, `movz w9,#<the float's upper half>,lsl #16`, gives every level the preset's scale. Docked, from the autosave in Link's house:

| Value | Scene → output | Upscaler |
|---|---|---|
| game | 1920x1080 → 2560x1440 (level 0, 0.75) | the network, or MetalFX |
| 1.0 Native | 2560x1440 → 2560x1440 | the game's network still runs, 1:1 (run with the game's own); MetalFX's spatial scaler leaves a 1:1 dispatch to it, the temporal one would anti-alias it (not run) |
| 1.5 Quality | 1743x981 → 2560x1440 | MetalFX temporal |
| 2.0 Performance | 1280x720 → 2560x1440 | MetalFX temporal |
| 3.0 Ultra performance | 854x480 → 2560x1440 | MetalFX temporal (content scale 3.0, its limit) |

Quality renders 1743x981, not the 1710x962 of the scale written (0.668): the caller multiplies by a ratio of the controller's own (`ctrl+0xe58 / +0xe50`), which 0.5 and 1.0 hit exactly. Dynamic resolution between two rates (Bananza's Softest) and Native (MetalFX AA) have no rows yet.

The profile's `res_chain` (`2560x1440 2560x1440 1920x1080 1.333334 3.0 1.333334`: the outputs docked and handheld, the palette's rates, and level 0 as the start) gives the settings window each rate's render size and the launch line `resolution: docked, output 2560x1440; upscale rate the game's own: 1.3333 to 3, starts at 1.3333; scene 1920x1080 to 854x480; …`, as the runs drew it: docked 1920x1080 → 2560x1440, handheld (`DM_OPMODE=handheld`) 1440x810 → 1920x1080, which the final copy then stretches to the 2560x1440 window.

## Found on this game

- The online library's [eventfd for its poller](../../../docs/reference/services.md#eventfds-served-offline) and the [virtual audio input list](../../../docs/reference/audio.md#output-streams-and-virtual-audio-devices-sdk-20-auddmgu) blocked startup.
- The SDK's [NDVE pack](../../../docs/reference/shaders.md#the-movie-librarys-ndve-shader-pack) contains 22 compute programs. The title route uses 11.
- The two NDVE programs named by its NDSR-form record table (`c2fc2ddd604c25e7`, `4f41ccf24f163e0d`) counted as [the game's upscaler](../../../docs/reference/rendering.md#a-games-own-upscaler-drawn-by-metalfx) beside agl's 56 (resolved statically: `upscaler_keys` leaves them out; not run with `DM_UPSCALER=metalfx` before or after).
- The [raw write log and pool lookup](../../../docs/reference/frame-rate.md#a-full-frame-shader-overflows-the-raw-write-log) took the windowed title movie from a 47.6 ms median to 16.67 ms on an Apple M5, at 1920×1080 decode. A steady 300-frame window averaged 60.0 fps and its GPU median was 15.94 ms. A simultaneous ten-worker shader build caused additional stalls. The same run returned to 60.0 fps when the build paused.
- A [play report send](../../../docs/reference/services.md#an-asynchronous-play-report-opens-prepou) aborted at the first gameplay transition after a failed `prepo:u` connection. A Mac dry run with the offline completion finished the 9,254-picture opening movie and continued submitting the live scene. The title-only shader set left the scene black.
- The white 3D scene was agl's [conditional depth clears](../../../docs/reference/rendering.md#conditional-rendering-evaluated-at-replay) run unconditionally (resolved; the profile sets `render_cond on`). The main opaque pass tests `EQUAL` against a copy of the prepass depth that agl clears under a condition right after copying, a clear the console skips. Without the key the copy was 1.0, no lit geometry passed, and the full-screen sky (`943d8c0ece545cc8`) showed through. With the key the saved Kokiri Forest scene renders: Link, the ground, the props, lighting and the HUD.
- Mesh-shaded models were missing, among them the door of Link's house: the split read six stage slots of each BNSH program, and NVN2 keeps [task and mesh shaders in slots 7 and 8](../../../docs/reference/shaders.md#task-and-mesh-shaders-in-nvn2-bnsh-program-slots-7-and-8) (resolved). The new split adds 491 mesh and 17 task shaders to the map, 53 of the 54 keys the Kokiri Forest scene had asked for. 511 of their 520 build; the door renders.
- Kokiri Forest ran at about 20 fps with the GPU two-thirds idle: the [bindless pool table was rebuilt for every registration](../../../docs/reference/frame-rate.md#a-bindless-pool-table-rebuilt-for-every-registration), and about 12,000 descriptors of finalized texture objects churned the ghost ring (resolved). The frame is now 16–21 ms at the median on an Apple M5, submit 5–8 ms, and the GPU (14–21 ms) is the limit.
- The first 3D scene exhausted Metal memory when [bindless pool walks churned finalized textures](../../../docs/reference/nvn-objects.md#a-bindless-pool-churns-finalized-textures-within-a-submission). On the Apple M5, the failing run reached 18,930 MiB of residency. With submission-local backing, residency was 7,946 MiB about ten seconds after the movie and 7,871 MiB at 35 seconds. The opening 3D scene and its subtitles presented, and the test host exited normally.
- Of the 42,851 shaders, 9 did not translate on chain a88f07209cee; 42,850 translate on chain 133cee187d36. 8 foliage mesh shaders stopped at a truncating [F2IP](../../../docs/reference/shaders.md#f2ip-two-floats-into-two-bytes) with source A `RZ` (hi word `0x0000c4ff`; three of them, `604134a5262ff670`, `ecead5cd0569091f` and `fed302d791a4ba43`, are drawn in Kokiri Forest; resolved), and `68bbe98b3bfd9876` (agl_common) has data in place of code. The foliage compute shaders `8692b34b521225be` and `83df46a0b1b379b4` (F2IP to the nearest) and the agl task shader `5d3a096025e375a1` (ISBERD mode `0xb8`) translate since chain 60cea4b16b6a.

## Open

- The scene asks for `d17eefaff4f0bc23`, whose code is in none of the shader archives.
- The title-only build logged 3,331 distinct mapped libraries it could not open, including 363 shaders that failed when setting up programs. A targeted build for those programs and their dependencies translated 6,132 of 6,134 shaders. The two failures, foliage compute shaders `8692b34b521225be` and `83df46a0b1b379b4` on Ampere opcode `0x243`, translate now ([F2IP](../../../docs/reference/shaders.md#f2ip-two-floats-into-two-bytes)).
- With `render_cond` on and the shader build still incomplete, Kokiri Forest showed a hard horizontal cut, sky colour above the horizon over the trees. The volumetric fog composite (`888c1068ac8f7043`, agl) takes a pixel whose R32Float depth copy reads above 0.9999 as sky and paints the sky lookup there. The pass that fills that copy draws with agl's full-screen vertex shader `fb1ed54be1baced1`, which that build had not reached yet, so the host skipped the draw (`draw skipped: no render pipeline`) and dropped the target's store. Retest with the stamped full build. The sky lookup's peaks (about 105, 67 and 36 in RGB) are unverified against the console.
- The opening scene calls `nvnCommandBufferDrawMeshTasksIndirect`, which the host does not implement. On `v0` the probe caught the return at `main+0x2be2dc0`; the branch builds the command buffer pointer in `x0` and the indirect argument address in `x1`. It does not set `x2` on that path. A separate sample of the first 64 bytes at the indirect address returned zeros after the call; the populated record's layout is still unverified. The title-only run logged 11 keys missing from the map. The expanded run captured seven of them before the memory failure. A byte-for-byte comparison found none of those seven code areas in the extracted shader package.
- The 3D scene's CPU cost (37–59 ms a frame, with pool walks of about 33,000 descriptors) is [resolved](../../../docs/reference/frame-rate.md#a-bindless-pool-table-rebuilt-for-every-registration). Open: the GPU's 14–21 ms a frame in Kokiri Forest, which still drops frames below 60 fps; TBDR optimizations are off for this bindless game (`DM_NVN_TBDR=1` turns them on), and attachments load and store about 330 MB a frame.
- The Nov. 4 Lichii branches offered two shader leads. The first, opcode `0x243`, is resolved: both of this game's forms translate ([F2IP](../../../docs/reference/shaders.md#f2ip-two-floats-into-two-bytes), derived from the game's own encodings). Its [floating-point global reduction](https://github.com/zortos293/Lichii/commit/3aa89d1cdbe58a2bd5ded06b9c615c78da2ade70) matches a separate `F32FtzRn` diagnostic in the Mac shader build, where the translator drops that operation. Neither of the two shaders in the sky lookup and draw uses those instructions or the gather opcodes from Lichii's [fog work](https://github.com/zortos293/Lichii/commit/375c4a472bd95fdfaae0de6e3f192499cd14f806).
