# The Legend of Zelda: Ocarina of Time (`0400486024DEC000`)

A Switch 2 game: update v131072, SDK 22.2.8 (`Ounce`). Nintendo EPD's engine (sead, agl, gsys, Havok, CRIWARE; project `Owl`, with Tears of the Kingdom's file layout) on NVN2. Modules `main`, `subsdk0` (NintendoSDK_movie) and `sdk`, no rewriter patches. Status: plays on the Mac through the title, the opening, a new file's first scene, Link's house and Kokiri Forest, with saves, at about 59 fps with the picture close to console video. Mac only so far.

## Profile

SDK 22.2.8, NVN API 231.40, with Nintendo's sead, agl and gsys. The three loaded modules are `main`, `subsdk0` (NintendoSDK_movie), and `sdk`. The NPDM declares 48 MiB of system resources. Startup requests a 6.20 GiB heap, which fits in the profile's 17.6 GiB reservation with the stack and alias regions. The registered builds are the supplied base dump (`v0`) and update `v131072` (1.1.1), which a NUP carries alone as the whole game: their three modules are the same builds, and v131072's shader split is v0's key for key, so the tables are v131072's (`package`, `shader_versions`).

## Mac dry run

Use the rewritten `patched_v0` and the original extracted `base/romfs`. Build the host with `make -C dm/host GAME=0400486024DEC000` and use the [Mac shader build](../../../docs/development.md#build-by-hand-mac). From the repository, set `DUMP` to the folder containing `base` and `WORK` to the build and run workspace beside it.

```sh
mkdir -p "$WORK/run/save" "$WORK/run/temp" "$WORK/font"
python3 dm/tools/make_ext_font.py "$WORK/font/nintendo_ext.ttf"
DM_ROOT="$WORK" DM_ROMFS="$DUMP/base/romfs" DM_SAVE="$WORK/run/save" \
  DM_TEMP="$WORK/run/temp" DM_MSL_DIR="$WORK/shader/cache" DM_FONT_DIR="$WORK/font" \
  DM_NVN_SHMAP="$PWD/dm/games/0400486024DEC000/shader_map.tsv" \
  DM_WINDOW=1 DM_METAL_HUD=1 DM_FOCUS_KEEP=1 DM_AUDIO=1 \
  dm/host/dmhost "$WORK/patched_v0"
```

`DM_FOCUS_KEEP=1` lets the title keep playing while another app has focus. The profile prewarms the 11 NDVE compute pipelines used by the title. On the Apple M5 that took 17.7 s on a cold run, with a progress screen, and 7 ms with the archive warm. Compiling the same pipelines during the first submission had blocked the first movie frame for tens of seconds. The larger scene shader set also triggers a separate graphics-pipeline prebuild. On the first run with that set, the startup screen took 86.9 s to hand out all pairs, and the remaining workers finished after 110.6 s total.

Start a new game to reproduce the opening scene transition. With the test save and title flow, `DM_KEYS=f2600:A,f2950:A` advances the menu automatically. `DM_NVN_SHDUMP` saves control sections and code for missing keys to the directory it names.

For a run past the opening, copy the committed save folder to the new run's `DM_SAVE` and load slot 00 from the menu. The checkpoint contains both `slot_00/progress.sav` and `slot_00/caption.sav`. The load screen identifies it as **Kokiri Forest Autosave**. A windowed reload reached the playable scene with the HUD and controls, so rendering can be tested without replaying the movie.

## Upscaler and resolution (current: static analysis of v131072's main, then headless runs from the autosave in Link's house)

- **The upscaler is agl's NDSR network, not FSR.** gsys's `Main.gsys__ModelSceneConfigParam.bgyml` sets `CreateNdsr` (the UI scene's does not) and `CreateFilterAa` (SMAA / FXAA); it has no `CreateDlss` key. `main` holds no FSR, EASU or RCAS string. agl's NDSR parameters (`aglndsr`, `main+0xcd8c50`): `enable`, `view_enable_mask`, `upscale_ratio` 1.0, `two_step_upscale_ratio_threshold` 4.0, `vr_upscale_ratio` 2.0, `vr_enable_dithering`, `vr_sharpening_amount`. NDSR's loader (`main+0xf51360`) opens three packs from `Lib/agl/agl_resource.Nin_Ounce_NVN2.release.sarc.zs`: `agl_ndsr.pck`, `agl_ndsr_vr.pck` and `agl_ndsr_vr_light.pck`, 59 compute keys in all.
- **Colour, read as the host reads it (`up_mfx_color`):** `agl_ndsr.pck` (header +4 `0x10100`) has 11 pairs, one with no curve (encoded in and out, for an 8-bit image) and one with a half-float decode (linear out), Star Fox's shapes (its `3fe6b091bb8c40ce` is here too). In the two `vr` packs the networks come in threes, as Bananza's do: one with a float encode and no decode (linear in, encoded out), a shape MetalFX does not draw yet, and two with no curve at all, which the host takes for encoded colour and draws only into an 8-bit image (into a float image they would be linear). Three small kernels in each (`f8965bffbdf51d78`, `ddc1143b7932a93e`, `3426ccfe7d691d0f` / `a335c1db6270c355`) look like helpers. In a run the game uses `agl_ndsr_vr_light.pck`: docked, the helpers `f8965bffbdf51d78` and `a335c1db6270c355` write the square roots of the scene's colour, and a network of the pack (`fa3033d05c0a41d6` at 1920x1080, `04135bb812a0d66e`, `aad7ea7e5c02f41d`, `d99fbeeb53d38847` at the other sizes) takes the 1920x1080 RGB9E5 scene to the 2560x1440 R11G11B10F output, which is the window's size (one resample; `present: picture shape 2560x1440`). MetalFX draws it ([An upscaler fed square-root colour](../../../docs/reference/rendering.md#an-upscaler-fed-square-root-colour)); taken as linear it washed the picture out.
- **Resolution:** `ModelSceneExtensionParam` (`Pack/Bootup`) gives the final image and base size per mode, 2560x1440 twice and 1920x1080 once, and a dynamic-resolution palette for each: 10 levels at 2560x1440 (`ResolutionReduceScale` 0.75 down to 0.3333, so upscale rates 1.33 to 3.0, load threshold 95) and 8 at 1920x1080 (0.75 to 0.4445, threshold 108). The scene never renders at the output size, so the network always runs. `main` queries no display size (no `oe::GetDefaultDisplayResolution` or `vi::QueryDisplayBufferMaxResolution`), and it imports `oe::GetCurrentGraphicsScale`, HDR status and 120 Hz / VRR queries.
- **Motion and camera:** `EnableMotionBuffer` and `MotionVectors3D` are off and there is no TAA, so MetalFX needs camera-only motion vectors from depth, as on [Donkey Kong Bananza](../040074A01BF12000/README.md#metalfx-temporal-scaling-and-frame-interpolation-current-opt-in-not-played-yet). agl's shaders name gsys's Context members (`cGSysCtxView`, `cGSysCtxProj`, `cGSysCtxViewProj`, `cGSysCtxInvView`, `cGSysCtxNearFarParam`, `cGSysCtxFovyParam`), and Bananza's `camera_mats` (`vertex 0 0x0 0x30`) holds (current, checked in a run with `DM_MFX_PROBE`): the opening's 3D cutscenes and Link's house give a GL perspective camera, 50 degrees, 16:9, near 0.1, far 25037, no projection offset (no jitter), in the 1920x1080 D32F depth pass that has the upscaler's input size; over 15,000 upscaler frames every one had motion vectors, one of them without a camera, and the cutscenes' cuts reset the history.

### Anti-aliasing (static analysis; not run yet)

- **What the frame has:** NDSR's own SMAA, ahead of the network in `main+0x251be0` (agl `SMAA_For_NDSR`). `main+0x14e3660` clears its edge target (a quarter of the scene's size, RG16Uint) and its weights (RGBA8); `main+0x14e3720` dispatches edge detection (`f8965bffbdf51d78`), blend weights (`d17eefaff4f0bc23`, indirect, over the edge list) and a compose (`a335c1db6270c355`) that blends the scene by the weights and writes the square-root colour the network reads. MetalFX takes that image, so SMAA comes before it. A second, render-pass form (`main+0x14e20a0`, with a stencil) is for other pack types; no run has drawn its programs.
- **`CreateFilterAa` is not in front of the upscaler.** agl's filter AA (`main+0xa052c0`, the object at post-process +0x500; `fxaa`, `smaa_*` in `agl_technique_pfx.sharcb`) runs when a config byte (+0x9a0, next to NDSR's +0x9c0; by its place, `CreateFilterAa`), its `enable` (post-process +0xc68) and a float (+0xea0, 1.0 by default) all say so, and then it runs instead of NDSR (`main+0x25abe0` branches past `main+0x2511b0`): a frame has one or the other, and MetalFX never follows it. What keeps it off in `Main` is not traced: every run drew NDSR, and none has built one of its programs. Of the 18 EnvSet files only `ActorCapture` names a `FilterAA` parameter. No row touches it: the UI scene has no NDSR, so a row would leave its captures with no anti-aliasing at all.
- **Setting patch:** with `DM_UPSCALER=metalfx-temporal`, Native (MetalFX AA) included, two rows leave out the edge and weight dispatches (`main+0x14e3a48`, `0x14e3a90`). The weights stay at their clear, the compose copies the scene, and MetalFX is the only anti-aliasing. Game and MetalFX spatial keep SMAA.
- **Replacing NDSR does not remove SMAA:** its dispatches come before the network, and the host's MetalFX takes only the network's. The edge kernel's image is smaller than its input and the compose has two textures, so `up_mfx_resolve` refuses both; the weights dispatch is indirect, which `up_mfx_encode` is not asked for. All three run as shaders and MetalFX reads the compose's output, so without the rows it takes SMAA's blends. With them its input is what every temporal run before [the weights were mapped](../../../docs/reference/shaders.md#programs-on-odd-entries-of-an-ndsr-pack) had: the compose over cleared weights.

### Render resolution (current, in a run)

**Render resolution** (`DM_UPSCALE_RATIO`, [`setting_patches.tsv`](setting_patches.tsv)) fixes the scale the game renders at. The dynamic-resolution controller (built at stage start by `main+0x31c3b30` from the palette's level entries: {scale, priority} nodes) returns the chosen level's scale from its update (`main+0x805aa0`) through `main+0x805ff0` (`fmov w9,s8`), and its caller (`main+0x31d3ee0`) makes it the scene's scale when the level changes or the stage starts. One word there, `movz w9,#<the float's upper half>,lsl #16`, gives every level the preset's scale. Docked, from the autosave in Link's house:

| Value | Scene → output | Upscaler |
|---|---|---|
| game | 1920x1080 → 2560x1440 (level 0, 0.75) | the network, or MetalFX |
| 1.0 Native | 2560x1440 → 2560x1440 | the game's network still runs, 1:1; MetalFX's spatial scaler leaves a 1:1 dispatch to it |
| native-mfx Native (MetalFX AA) | 2560x1440 → 2560x1440 | MetalFX temporal at the output's size, the same word as 1.0, only with `DM_UPSCALER=metalfx-temporal` |
| 1.5 Quality | 1743x981 → 2560x1440 | MetalFX temporal |
| 2.0 Performance | 1280x720 → 2560x1440 | MetalFX temporal |
| 3.0 Ultra performance | 854x480 → 2560x1440 | MetalFX temporal (content scale 3.0, its limit) |

Quality renders 1743x981, not the 1710x962 of the scale written (0.668): the caller multiplies by a ratio of the controller's own (`ctrl+0xe58 / +0xe50`), which 0.5 and 1.0 hit exactly. **Dynamic resolution** (`DM_UPSCALE_DYNAMIC=1`, sharpest `DM_UPSCALE_RATIO`, softest `DM_UPSCALE_SOFTEST`) keeps the controller stepping and maps its palette onto the chosen range, `s' = a s + b`, in seven words of padding after the update ([`setting_patches.tsv`](setting_patches.tsv)). Checked with Quality to Ultra performance: 1743x981 in Link's house, where the game stays at its first level, and 854x480 with the load threshold zeroed by a test row, which sent the controller straight to its last level. The levels between were not seen. Handheld's palette ends at 0.4445, so it stops short of the softest.

The profile's `res_chain` (`2560x1440 2560x1440 1920x1080 1.333334 3.0 1.333334`: the outputs docked and handheld, the palette's rates, and level 0 as the start) gives the settings window each rate's render size and the launch line `resolution: docked, output 2560x1440; upscale rate the game's own: 1.3333 to 3, starts at 1.3333; scene 1920x1080 to 854x480; …`, as the runs drew it: docked 1920x1080 → 2560x1440, handheld (`DM_OPMODE=handheld`) 1440x810 → 1920x1080, which the final copy then stretches to the 2560x1440 window.

## Frame rate

Measured on an M6 Mac with 16 GB, headless, on one walk with camera turns (`walk.sh` in the work folder).

- Current: the title and menu, a movie behind them, are a locked 60 fps (p50 16.67 ms, GPU span 15.6 ms).
- Current: walking the village at the game's top internal resolution, 1536x864: a locked 60 fps, mean 16.67 ms over each settled window. Per 2,700 frames: 0-8 frames over 25 ms and 0-2 over 33 ms. Frame p95 17.8-18.9 ms with no window, as the game's own loop moves around its fence wait; in a window p95 17.8 ms, 3 over 25 ms and 5-16 over 18 ms per 600. GPU span p50 16.5 ms, summed GPU 15.8 ms, CPU 6 ms, about 101 passes a frame. The heavy stretch where the village opens (about 1,560 draws) holds 16.65-16.8 ms by lowering its resolution, then returns to full. The main pass used to sit at 763x429 at the same GPU time: [marked shaders tested depth late](../../../docs/reference/frame-rate.md#a-hosts-own-store-in-a-fragment-shader-moves-its-depth-test).
- Before [pool shaders stopped counting as depth readers](../../../docs/reference/rendering.md#pool-shaders-taken-as-depth-readers): passes 118, 104, 219, 224 in a four-frame cycle, frame times 15, 15, 18, 18.5 ms, mean 16.9 ms. Half the frames rendered the reflection probe's faces with one draw a pass.
- The host's GPU figure adds up command buffers, which overlap, so it reads above the real span: 17.5 ms was never a frame's real time. The real span is `@gpu_end_ms − @gpu_beg_ms` in `DM_NVN_TSV`, or the `first start to last end` of `DM_NVN_GPUPROF`.
- The roughly 1 ms the [wind fix](../../../docs/reference/shaders.md#dead-code-removal-dropped-a-coordinate-of-a-multi-output-instruction) seemed to add: 0.66 ms of it is the upscaler, 416 → 1076 µs, because its variants then read what they had lost. It is doing its real work.
- Attachment traffic was not the cost it looked: 254 MB load and 277 MB store remain, and the cheapest passes move 20 MB in about 30 µs. The pass count was the cost.
- Resolved: 25-40 ms frames while the GPU sat idle with the next command buffer committed, 51-75 per 2,700 in a bad run: [the GPU idles with the next command buffer already committed](../../../docs/reference/frame-rate.md#the-gpu-idles-with-the-next-command-buffer-already-committed). What holds Metal's submission queue in the kernel is still unknown.
- The title movie's network takes 15.4 ms of compute a frame here, so the title holds 60 fps with almost nothing to spare, and slower GPUs fall below it: [issue 1375](https://github.com/seedds/nxnative/issues/1375), 35 ms on an M1 Max.
- In a run that takes shots, each shot costs its frame 60–100 ms, and `DM_NVN_GPUPROF` and pass dumps slow the frames they cover.
- Open: frames of 100–650 ms when an area first loads (640 first uploads, 321 MB, in one frame of 294 ms; another 640 ms of submit with 68 MB).
- `DM_NVN_TBDR=1` was tried and does not help: p95 19 ms on the same walk, against 17.8.
- The first long run on a new chain is slower (p50 60–114 ms), while `MTLCompilerService` compiles pipelines; the next run is not.
- With a window, the first start on a new chain runs the pipeline prebuild first: 33,190 shader pairs, 691 s on this Mac. A run with no window skips it.
- The opening movie runs at the movie's own 24 fps pace during the story section and cannot be skipped: about 8 minutes on a new file.

## Memory

- Current: on the walk, run from an external drive with a 3.5 GB pipeline archive: resident 10.9-11.4 GB, wired about 9.4 GB, on a 16 GB Mac. `vmmap` and `footprint`: 6.4 GB of guest memory and 3.8 GB of Metal textures and targets, 1 GB of IOAccelerator memory. [Reading the archive into memory](../../../docs/reference/memory.md#a-pipeline-archive-on-an-external-drive-is-read-into-memory) used to add 3.5 GB (footprint 15.0, peak 16.7). `mem_map_limit on`: a map past the application pool fails as on Horizon, and the SDK's allocator then gives back the pages it keeps. Other apps' memory adds to the swap: other games running beside it can push the Mac over.
- This game took the Mac down before the fixes (kernel panic in `IOGPUGroupMemory` at 14.7 GB wired): [raw pool table](../../../docs/reference/memory.md#memory-pools-nothing-gave-an-address-to-stay-out-of-the-raw-pool-table), [textures made only when read](../../../docs/reference/memory.md#shaders-report-which-textures-they-read-through-a-pool) (upstream's route; here a walk makes every texture with content: [a pool walk's entry](../../../docs/reference/nvn-objects.md#a-pool-walk-gives-every-registered-id-a-texture-of-its-own)), [out-of-memory exit](../../../docs/reference/memory.md#repeated-gpu-out-of-memory-failures-end-the-game).
- Why so much: the game's own memory is about the console's 9 GB application pool, and on the Mac its textures also exist as Metal textures, as Metal cannot sample the guest's block-linear storage.
- Open: render targets that move in the game's pool and change size with its dynamic resolution (1580 → 1579 → 1578 …) get a new Metal texture each time, about 2 GB added to the residency set per 300 frames. It costs about 0.5 ms a frame once settled, so recycling them is a smaller win than the walk, but [a report of a GPU driver panic](https://github.com/seedds/nxnative/pull/1299) lines up with this churn.

## Open

- Open: [the movie network](https://github.com/seedds/nxnative/issues/1375) takes 35 ms a frame on an M1 Max, so movies and the title run at about 28 fps there. It fits on this M6, with about 1 ms to spare.
- Current: against a frame of console video of Navi's close-up the picture matches: hair and sign within 1–2 % in red and green. The causes, each general: [float atomics](../../../docs/reference/shaders.md#float-atomics-in-storage-memory) (too bright, yellow skin, a pale veil: the exposure read back from buffers that stayed 0), the terrain's CPU-written maps (holes, wrong materials; the profile keys above), [the gather offsets](../../../docs/reference/shaders.md#texturegatheroffsets-and-a-loop-over-its-offsets) (the dotted rows in blurred areas, born in the NDSR upscaler, three pictures from one input), and [image atomics on RGBA8](../../../docs/reference/shaders.md#image-atomics-on-a-32-bit-colour-texture) (the anti-aliasing's blend weights).
- Current: the grass no longer flickers. Its blades shifted at 10 Hz because the wind's pressure solve read one neighbour at an undefined row ([dead-code removal](../../../docs/reference/shaders.md#dead-code-removal-dropped-a-coordinate-of-a-multi-output-instruction)), so the velocity field (512x512 RGBA16F, a two-buffer ring) held strong stripes up to ±11 with a 6-frame cycle. In the moss on the bridge, the mean difference between adjacent frames fell from 5.97 to 0.70 of 255, and it now grows smoothly with the lag.
- Open, small differences from that same console frame: Navi's core has a harder edge and a narrower glow here (the bloom texture peaks at 0.44; the ball's HDR is about 0.9 with a tiny spot at 45); shadows are less blue, and the far grass about 1.4 times brighter. One frame of compressed video is weak evidence for either. The falling leaves look dark near the camera, not compared.
- A red `texture type mismatch` on `9b310b3349825e9a` (a UI merge shader): a 3D texture left bound in a slot its active branch does not sample. Harmless so far.
