# Donkey Kong Bananza (`040074A01BF12000`)

A Switch 2 game: update v458752 over the base game, SDK 20.5.19 built for the Switch 2 (`sdk` names its spec `Ounce`), NVN2. Nintendo EPD's engine (sead / agl / gsys, Phive), modules `main` + `sdk`. **Plays on the Mac** (M4 Pro): three play sessions of about 5 minutes each and scripted runs of up to 15,900 frames, through the opening, the mining tunnel and the areas after it, with the guide movies in their panel, at 60 fps; in busy scenes the game drops itself to 30 fps for a few seconds ([Open](#open)). The first start with no pipeline archive builds the pipelines for about 4 minutes, once. Nothing past the first level's opening areas is tested; iOS is untested.

## What it needs

| Setting | Where | Why |
|---|---|---|
| `sys_resource 0x0` | [`game.tsv`](game.tsv) | the NPDM declares no system resource: virtual address memory off, the game sets a heap. Without the key the host answers 32 MB, and the SDK's VammManager then maps memory up front (GetInfo 0x21) |
| `app_pool 0x240000000`, `mem_reserve 0x270000000` | `game.tsv` | the Switch 2 leaves games 9 GB of its 12 GB (not measured here); with a Switch 1 pool (3.2 GB) the game's heaps did not fit: `AudioSystemHeap` creation returned null (`main+0x564b48`) |
| `romfs_marker System/Resource/ResourceSizeTable.Product.rsizetable.zs` | `game.tsv` | a file every version has |
| `render_cond on` | `game.tsv` | agl's render buffer binding wraps its clears in render conditions (`SetRenderEnableConditional` at `main+0x12798c`, before the `ClearColor` at `main+0x1279d4`); drawn unconditionally, a clear-only rebinding of the composite target right after the composite draw wiped it before the upscaler read it, and every gameplay frame was black |

## Files

- Built from a dump folder (`base/`, `updates/458752/`, `dlc/040074a01bf13001/`): `build_ipa_from_nsp.py <folder> --platform mac-app` packs it with [`scripts/pack_dump.py`](../../../scripts/pack_dump.py), with no keys; the app has no icon, as a dump has no control data. The update's RomFS is the patched one (80,273 files, 8.6 GB; it drops 42 base files, among them the `Product.100` tables its `Product.200` ones replace), so it is packed on its own. The DLC (add-on content index 1, 8,000 files, 0.9 GB) mounts as `EmeraldRush`.
- Shaders: `Shader/*.Nin_Ounce_NVN2.bfsha.zs` (BNSH) and `Shader/Project.Nin_Ounce_NVN2.release.sarc.zs`. The code is Volta / Ampere's 128-bit encoding (`0x794d` EXIT, `0x7918` NOP), not Maxwell's.
- NVN2 control sections (dumped with `DM_NVN_SHDUMP`): magic `0x98761234`, version `0xc9`; +0x38 the instructions' length (SPH included), +0x40 that rounded to 0x100, +0x44 the code area's (the c1 segment lies between the two), +0x4c the register count, +0x58 compute's thread group. Their own length is at +0x30 in BNSH files only (0xd8; 0xd0 in effects, 0 in agl's BAHS and in memory), so the shader key hashes the first 0x48 bytes with +0x30 zeroed, plus the code area (`hle_nvn.c` `nvn_ctl_lens`, `shader_split.py` `key_ctl`).
- agl's upscaler is an `NDSR` pack, `agl_ndsr.pck` in `Lib/agl/agl_resource.Nin_Ounce_NVN2.release.sarc.zs`: 16-byte records from +0x10 (control section offset, control length << 4 | type, code offset, code length / 16 << 8 | type) up to a zero one; 30 shaders (3 vertex, 3 pixel, 24 compute: a small network on the tensor cores, HMMA, LDSM, MOVM). `shader_split.py` `ndsr_shaders` reads it, and pairs each vertex record with the pixel record after it. All 24 compute variants encode linear input; they come in threes by output: encoded, linear clamped to 0-1, linear up to 128 ([An upscaler's colour read from its code](../../../docs/reference/rendering.md#an-upscalers-colour-read-from-its-code): MetalFX draws the 16 linear ones, the 8 others keep the network; not run on the game since, as its libraries are of an earlier chain).
- The split reads the bfsha / BNSH files, agl's BAHS archives (`agl_common.sharcb` and the others: 1,555 shader records, one more than the archive counts, so the record check allows 1 % of strays) and sead's primitive drawer: 22,852 shaders (with the 30 of the NDSR pack).
- [`geo_mesh.tsv`](geo_mesh.tsv): the game's one vertex / geometry pair (`f9c807930abd1234` with the passthrough kernel `5d537f7630ec3671`), which draws every geometry draw, about 600 a frame; built as a mesh library of 16 triangles a group ([Mesh geometry groups sized to the vertex output](../../../docs/reference/shaders.md#mesh-geometry-groups-sized-to-the-vertex-output)).
- The prewarm seed list, [`pso_manifest.tsv`](pso_manifest.tsv) (3,793 lines: 1,726 shaders, 2,030 render pipelines, 37 compute pipelines), is the Mac's device list of the play sessions before the host read device lists without a seed list ([development.md](../../../docs/development.md#prewarm-lists)): boot, the title, the opening and its guide movies, the mining tunnel and the areas after it, recorded with prewarm off. A start with no device list builds it in about 8 s before the first frame.

## Shaders

The translator decodes Ampere code natively (job `arch: sm86`; [Ampere shader code](../../../docs/reference/shaders.md#ampere-shader-code-switch-2)): all 22,852 shaders translate (chain 6f41726ef36d). NVN2 keeps NVN's texture handle table in c[2] (0x20 + 8 slot) and the graphics stages' storage buffer tables in c[0] (0x110 vertex, 0x510 pixel); compute lays out c[0] per shader from its control section, push constants first ([Ampere shader code](../../../docs/reference/shaders.md#ampere-shader-code-switch-2)). The upscaler pushes (1 / w, 1 / h, w, h) of its target for its graphics passes and the source and destination rectangles for its compute network.

## Rendering

The scene renders into 1676×943 targets (R11G11B10F colour), agl's upscaler takes it to 2304×1296, and that is copied to the 2880×1620 window. On the way to the first picture:

1. The upscaler's network did not translate (HMMA and the other tensor instructions): the window kept the output's clear colour (0.3, 0.3, 1).
2. Six effect compute shaders (`d076142721d836a5` and others) did not load: a storage address was a c[0] entry plus an offset from c[1], and the translator took the c[1] term as the base.
3. Black frames: the composite was cleared before the upscaler read it (`render_cond`, [What it needs](#what-it-needs)).
4. Black speckles and white blotches over a dark frame: NaN from the environment cube's mip chain ([Mip-chain pass sampling the level it renders](../../../docs/reference/rendering.md#mip-chain-pass-sampling-the-level-it-renders)). Found with raw dumps (`DM_NVN_SNAPRAW`) of the R11G11B10F targets, `DM_NVN_HILITE` to narrow the shaders (`cca896efc6bb7c21` and `c8637178e2818d18` wrote most of them), then those shaders' MSL instrumented to record their first NaN temporary: a fetch of the prefiltered cube, back through the prefilter to the cube's own mip passes.
5. Woven rock surfaces and holes in the rock: the textures the game loads were untiled in the Tegra X1's order inside a GOB ([The Switch 2's order inside a GOB](../../../docs/reference/nvn-objects.md#the-switch-2s-order-inside-a-gob)). The rock material's albedo (ASTC 8×8) written straight to its output looked right and its BC7 normal map did not, so the BC7 file (`BaseRock000_Pnrm`) was decoded offline in every order of the GOB's address bits.
6. The geometry shader `5d537f7630ec3671` (no vertex output: it writes its primitives to memory with ATOMG / STG) needed LEPC, OUT and ISBERD, and `7529699c7b7e49c0` (ActionLibraryPass compute) MATCH; with them all 468 shaders of the first gameplay minute translate.
7. Black tunnel walls and floor, with only the loose rocks and Donkey Kong drawn (compared with a YouTube capture of the same spot): the terrain's colour pass, about 400 indirect draws, drew nothing.
   - **How the terrain is drawn:** each chunk's depth prepass runs the culling geometry shader `5d537f7630ec3671`. It writes the surviving triangles' indices and adds their count to the chunk's indirect draw record (64 bytes, bound as its storage buffer 0). The colour pass draws from that record.
   - **What was wrong:** the records held instance count 0, and their counts grew frame after frame. Every frame gsys's vertex shader `c9a56f796ea4a4cd` (96 points or more) writes {count 0, one instance} into each record whose address its storage buffer lists. The translator had dropped those stores ([Global memory at an address loaded from memory](../../../docs/reference/shaders.md#global-memory-at-an-address-loaded-from-memory)).
   - **What NVN2 does:** decoding NVN2's indirect draw macro showed that instance count 0 draws nothing and the draw never resets the record.
   - **Now:** the walls, floor and lit passage draw as in the capture, at 60 fps.

### MetalFX temporal scaling and frame interpolation (current, opt-in, not played yet)

`DM_UPSCALER=metalfx-temporal` and `DM_MFX_INTERP=1` ([temporal scaling](../../../docs/reference/rendering.md#metalfx-temporal-scaling-at-a-games-own-upscaler), [frame interpolation](../../../docs/reference/rendering.md#metalfx-frame-interpolation-at-a-games-own-upscaler)) need the camera, the profile's `camera_mats` (`vertex 0 0x0 0x30`). Found statically and in a captured frame (F2724-F2726 and frame 3000, docked):

- **Camera:** gsys's Context block (0x970 bytes, binding 0 in the game's BAHS shaders, bound at vertex uniform 0 of the scene passes, size 2432): `cGSysCtxView` (3x4 rows) +0x0, `cGSysCtxViewProj` +0x30, the projection +0x70, `cGSysCtxInvView` +0xb0, `cGSysCtxNearFarParam` +0xe0, `NearFarParam2` +0xf0 (its z is the aspect ratio), `NearFarParam3` +0x100, `cGSysCtxFovyParam` +0x110 (its z the field of view, 45 degrees). GL projection, near 1, far 10000, depth not reversed; the window origin is the upper left once the game is running.
- **No jitter:** the projection's x / y offsets are 0 (high confidence for the frames seen; `cProjOffset` is a shadow / light parameter). **No velocity buffer:** agl's `smaa_resolve` and `fxaa_reprojection` read one, but none of their shaders is in the prewarm list of the play sessions, and the captured passes have no render-resolution velocity target (high confidence for gameplay; other scenes unchecked).
- **Depth:** D32F at the upscaler's input size (1676x943 in the capture), its serial new every frame (dynamic resolution); the upscaler `7629d857a0a93833` reads the scene's R11G11B10F texture and writes the 2304x1296 R11G11B10F output, the UI is drawn into that output (passes after it), and `e9c6f339b7550c71` copies it into the 2880x1620 sRGB window texture.

### Shadow settings

Current, opt-in, not played yet. Two settings in the Mac settings window's Advanced settings (Effects) are [setting patches](../README.md#setting-patches) of main v458752 (`e25c90c1…`), in [`setting_patches.tsv`](setting_patches.tsv). They were cheats before (`E25C90C1C1366388.txt`, written from the same static analysis), and they apply at launch:

| Setting (variable) | Values | Words |
|---|---|---|
| Shadow resolution (`DM_SHADOW_RES`) | `game` (default), `full`: Full (no dynamic scaling) | `main+0x81914` `1E21CC00` (`fcsel s0,s0,s1,gt`) → `1E2E1000` (`fmov s0,#1.0`) |
| Shadow map size (`DM_SHADOW_MAP_SIZE`) | `game` (default, 2048), `3072`, `4096` | `main+0x6edf74` `5281001A` (`mov w26,#0x800`) → `5281801A` / `5282001A`; `main+0x6ee01c` `F2C1001A` (`movk x26,#0x800,lsl #32`) → `F2C1801A` / `F2C2001A` |

- **What they change (static analysis):** gsys's per-frame shadow size (`main+0x8186c`, for each shadow view from `main+0x81140`) is the preset size × max(render width / 1920, render height / 1080), clamped to the preset, aligned to 8. With dynamic resolution at 1676×943 that is 1792, at 1152×648 it is 1232; `full` keeps the preset size. The preset size is 2048 in all four quality presets (Console, Handheld, UltraQuality, HighQuality), built at each stage start (`main+0x6edda4`); the two words make all four ask for 3072 or 4096. Since the patch is in place before the first stage, the size holds from the start.
- **Risk:** where the shadow texture is allocated was not found (probably a render-graph transient sized per frame). At 3072 or 4096 the shadows may be cut off if the texture stays 2048, or the game may crash when another screen (the map, menus) allocates its own targets from a fixed pool, as Pokémon Violet's 2K shadow mod did (GitHub issue #436). 4096 costs 4× the texels (32 MB at D16, 64 MB at D32) and more GPU time: the frame-rate controller may drop to 30 fps more often.
- **Checked:** every word against the update's `main` and the rewriter's output (`cheat_anchor.py settings 040074A01BF12000 --nso …/extract/v458752/ExeFS/main`: originals hold, none rewritten or moved). The host logs `setting DM_SHADOW_RES=full (Full (no dynamic scaling)): 1 word written: main+0x81914 1E21CC00 -> 1E2E1000`.
- **With the cheats:** while a setting holds its words, the shadow cheats of the same words are off for the session (the log says so); leave them off and use the settings.

### HDR highlights

Current, not played yet. With **HDR** on (`DM_HDR=1`) the brightest pixel stayed at 270-311 nits whatever peak the display reported (866 nits on the Mac it was measured on). The peak reaches the game, and the compose pass's top is peak / paper white (4.27); the cap is the first stage of that pass (agl's `alHdrCompose`, shader `6a6a033df5238f0a`): each channel goes through a normalised logistic of steepness K, `n(c) = (s(K(c - w)) - s(-Kw)) / (s(K(1 - w)) - s(-Kw))` with w 0.5 (`DRSigmoidMid`), then L = 1 - exp(-luma(n)) and the shoulder (knee 0.65, exponent 0.75, top M = peak / paper white). With K = 1, n saturates at 2.53, L at 0.92, and the shoulder at 1.33 × paper white. A fit to a captured frame pair gives K 0.996, w 0.484 (RMS 0.0073 with M = 4.27). `main+0x1b9af0` `ldr s1,[x11,#0x18]` (`BD401961`) loads K, `DRSigmoidGain`, from the stage environment (an AGL parameter node, `[env+0x708]+0x18`) into the pass's constants (`main+0x1b9b10`). Every stage uses its class default, 1.0: none of the 109 Env archives of v458752 (982 `bprojgfxbase` and 89 `bssprojgfxbase` variants, base and update layered; the DLC has none) sets it, and nothing writes it at run time. Static analysis and the fit, in `<NSP folder>/040074A01BF12000-work/hdr-peak/`.

The fix is a setting patch with no setting of its own: rows of `DM_HDR` `1` in [`setting_patches.tsv`](setting_patches.tsv) replace the load with `fmov s1,#K`, one row per band of `hdr_peak` (the reported peak / paper white, known at launch from `DM_HDR_PEAK` or the screen's headroom). Each band's K is the largest `fmov` encodes whose modelled ceiling is at least 98 % of the peak: 0.5 up to 1.08, 0.4375 to 1.19, 0.375 to 1.38, 0.3125 to 1.81, 0.25 to 3.31, 0.21875 to 5.98, 0.1875 to 15.6, 0.15625 above (at 866 / 203 = 4.27: K 0.21875, ceiling 4.22 × paper white, about 856 nits). The host logs `setting DM_HDR=1 (K 0.21875 (modelled ceiling at least 98 % of the peak)): 1 word written: main+0x1B9AF0 BD401961 -> 1E299001 [hdr_peak 4.27: peak 866 / paper white 203 nits]`.

- **Replaces the stage's value:** a constant instead of the environment's K, which is 1.0 in every stage of v458752. An update whose environments set another K would lose it while HDR is on (the patch is bound to this build anyway).
- **Never in SDR:** without HDR, or on a screen without headroom at launch, nothing is written (the SDR picture's highlights would clip harder). A window moved to another screen keeps the K chosen at launch.
- **What changes:** highlights (sun, lava, sparkles, bright sky) reach the peak; upper midtones get a little brighter (in the model, scene luma 0.75-1 goes from 0.77 to about 0.9); shadows and low midtones do not change. Very bright coloured highlights can reach the peak per channel (a hue shift at the clip).
- **Checked:** the word and its original on the update's `main`, not one the rewriter changed (`cheat_anchor.py settings`); the bands against the model at every 0.005 of `hdr_peak`. Not seen on screen yet. The `HDR highlights …` cheats of the same word are off in a session where the patch was written (the setting wins).

### Single upscale (current, opt-in, not played yet)

`DM_SINGLE_UPSCALE=1` (the Mac settings window's **Output resolution: Window**, Advanced settings; it was **Single upscale**) makes the game upscale once, from its render size straight to its window, instead of to 2304x1296 and then again to the window ([Upscaling once, to the game's window](../../../docs/reference/rendering.md#upscaling-once-to-the-games-window)). Found statically on main `E25C90C1C1366388` (nothing run yet):

- **The window:** a fixed 2880x1620, whatever the mode or the host's screen: nnMain passes it to sead's framework (`main+0x5bf0d8`; the getters `main+0x5bf770` / `main+0x5bf780` return 2880 and 1620). The game queries no display size: `main` imports neither `oe::GetDefaultDisplayResolution` nor `vi::QueryDisplayBufferMaxResolution`, so no host answer changes it.
- **The upscaler's output:** the root task's prepare (`main+0x539908`) builds gsys's display argument (`main+0x539c9c`): per display, sizes (display 0: the window, 2880x1620; display 1: 1920x1080) and three scales, {1.0, 0.8, 2/3} for both, which the display manager (the root task's +0xd8) copies (`main+0x713560`: display blocks of 0x64 bytes at +0xd0, sizes at +0x4, scales at +0x44, the current scale at +0x5c). Each frame `main+0x30f840` picks the display by the manager's byte +0x1c4 (handheld: `oe::GetPerformanceMode` is not Boost) and the scale by +0x1c7 (`oe::GetCurrentGraphicsScale`'s tier 0 / 1 / 2, stored at `main+0x549324` and on its change notification at `main+0x31e9b4`), and sizes the frame buffer by size x scale. With the host's answers (tier 1 docked, 0 handheld) that is 2880 x 0.8 = 2304x1296 docked and 1920 x 1.0 = 1920x1080 handheld, the upscaler's output, the UI's target and the source `e9c6f339b7550c71` copies to the window (high confidence: the code, and both sizes exact).
- **Not a host answer:** tier 0 docked would also pick 1.0, but the same tier picks the {3, 12, 16} parameter whose value less 3 (0, 9, 13) the dynamic-resolution controller takes into its GPU time (`main+0x38d180` → +0xe8, read at `main+0x38db98`), so the stub below changes only the scales.
- **The stub:** `patches.py` (`FRAME_STEP`, state page +0x38, capability `SINGLE_UPSCALE` in the rewriter table) sets every scale to 1.0 when the flag is set, at the constructor's stores (`main+0x539d6c`), so docked the output is the window's 2880x1620 and the final copy is 1:1. Handheld is unchanged: its display is 1920x1080 at scale 1.0 already, and its final copy still scales that to the 2880x1620 window. Off (the default), the constructor runs as shipped. The state page also takes `DM_FPS_TARGET`, which no stub of this build reads: leave it unset (a value would make the host pace frames by a frame step the game does not follow). It needs the app rewritten with this tree (the NSP script); the host logs `main: single upscale on` at start and `upscaler: output WxH (from WxH), the window's size: one resample` at the first upscale.
- **Dynamic resolution:** the scene size is the output divided by an upscale rate: 1.0 (no upscaler), or 1.375 to 2.0 with it (`main+0x38db98`, `SystemData/ProjectGraphicsParam` Default: `NdsrUpscaleMinRate` 1.375, `NdsrUpscaleMaxRate` 2.0; the capture's 1676x943 is 2304 / 1.375). The rates stay, so agl's NDSR network (or MetalFX in its place) sees the ratios it always does and no MetalFX upscaler is needed; the sizes are 1.25 times larger: 2095x1178 at 1.375, 1440x810 at 2.0, 2880x1620 at 1.0, up to 1.56 times the scene pixels. The frame-rate controller (`main+0x204a18`) and the rate controller measure GPU time, so they step down sooner.
- **Knock-on effects:** shadows scale with max(render width / 1920, height / 1080), capped at the preset (2048): 1.09 at 2095x1178, so the full 2048 in more frames. Memory: where the scene's targets come from (a heap sized at boot or the per-frame transient memory) was not found; a too small one would show as missing passes or a crash. The UI is drawn into the output at its size: the game runs scale 1.0 itself in handheld mode (display 1), but no docked frame at 2880x1620 was seen. The window stays 2880x1620 when the Mac window is resized: the host's present scales it to the drawable, as before.
- **To test:** docked, `DM_SINGLE_UPSCALE=1`; compare the HUD and scene sharpness and the frame rate in a heavy area with it off; watch the log for the two lines above, and for `[RED]` lines, missing passes or a crash on entering a level.

### Resolution model (current, opt-in, not played yet)

A PC-style choice of resolution in the Mac settings window (Advanced settings), under **Resolution**: **Output resolution** (`DM_SINGLE_UPSCALE`, [above](#single-upscale-current-opt-in-not-played-yet)), **Game's upscaler** (`DM_UPSCALER`), **Render resolution**, **Dynamic resolution** and **Softest**; then **Effects** (**Effects resolution** and the [shadow settings](#shadow-settings)), **Frame rate** ([Frame rate lock](#frame-rate-lock-current-opt-in-not-played-yet), frame interpolation) and **HDR**. Render resolution, Dynamic resolution, Softest and Effects resolution are [setting patches](../README.md#setting-patches) of main v458752 in [`setting_patches.tsv`](setting_patches.tsv). The scene is the upscaler's output divided by an upscale rate; the player sets that rate, fixed or as a range, and the effects can stay at the scene's size. Each rate option shows its render size for the console mode and output resolution chosen (`rate_base`, from `res_chain`), and the section's footer the size range and what it is upscaled to. Found statically (main `E25C90C1C1366388`, the captures' sizes); nothing run yet.

| Setting (variable) | Values | Words |
|---|---|---|
| Render resolution (`DM_UPSCALE_RATIO`): the fixed rate, or with dynamic resolution the sharpest | `game` (default), `1.0` Native (no upscaler), `1.5` Quality, `1.6875` Balanced, `2.0` Performance, `3.0` Ultra performance (fixed only, and only with `DM_UPSCALER` `metalfx` or `metalfx-temporal`) | fixed: `main+0x38dbc4` `tbz w8,#1` → `b main+0x38de6c`; `main+0x38de6c` `ldr s8,[x20,#0x2c]` → `fmov s8,#R`; `main+0x38df08` `ldr s0,[x9]` → `fmov s0,#R`. Either way: `main+0x16053a4` `ldr s0,[x9]` → `fmov s0,#R` |
| Dynamic resolution (`DM_UPSCALE_DYNAMIC`) | `0` (default), `1` (with `1.0` to `2.0`) | instead of the fixed three, R's eleven: the controller's bounds `main+0x38dd04` / `0x38e194` (min) → `fmov #1.0`, `main+0x38dd98` / `0x38e104` (max) → `fmov #2.0`; the clamp (below) |
| Softest (`DM_UPSCALE_SOFTEST`) | `1.0`, `1.5`, `1.6875`, `2.0` (default), `3.0` (only with a MetalFX upscaler); never sharper than R | `main+0x38dec4` → `fmov s0,#F`, `main+0x38dec8` → `fminnm s8,s8,s0`, `main+0x38e278` `fmov s2,s4` → `fmov s2,#F` |
| Effects resolution (`DM_EFFECTS_RES`) | `game` (default, half), `full` | `main+0x424a64` `fmov s11,#0.5` → `#1.0`; `main+0x423c74` `fmov s3,#0.5` → `#1.0`; `main+0x423d64` `fmov s2,#0.25` → `#1.0` |
- **The rate (static analysis):** the dynamic-resolution controller `main+0x38db98` runs each frame from `main+0x38d564` while the renderer's flag +8 bit 2 is set, with the current scene entry (+0x29 dynamic on, +0x2a upscaler on, +0x2c the entry's fixed rate). It keeps a ring of GPU times and walks a table of up to 9 rates (`[[main+0x26ce408]+0x78]`, count at +0x24; built at run time, not read statically) from the current one, stored at +0xc of the rate state `[[ctrl+0xf0]+0x270]` (+0 upscaler on, +8 a ceiling from agl's NDSR parameters). Over budget it steps toward cheaper rates up to `NdsrUpscaleMaxRate` (`main+0x38e0f0`); under budget it steps toward sharper ones only while the rate is above `NdsrUpscaleMinRate`. Rate 1.0 is the game's own no-upscaler path: the controller clears its upscale flag and the -0.5 mip bias (`main+0x38e0d0`), and the scene is the output size; it is where the controller sits until a frame is over budget (the 2304x1296 it held with GPU times of 0, [GPU timestamps per submission segment](../../../docs/reference/frame-rate.md#gpu-timestamps-per-submission-segment)). Rates seen: 1.0, 1.375 (1676x943), 12/7 (1344x756), 2.0 (1152x648).
- **Where the bounds come from:** `NdsrUpscaleMinRate` / `MaxRate` are agl parameters (config +0x5c8 / +0x5d0, value at +0x64) registered with the code defaults 1.375 and 1.9 (`main+0x4ca8a8`, `main+0x4ca92c`); `SystemData/ProjectGraphicsParam.alsarc` Default sets 1.375 and 2.0, and 2.0 is what the game reaches, so RomFS overrides the code. The controller is their only reader (four loads), so patching those loads covers both.
- **The fixed rate:** every frame takes the controller's fixed-rate path (as for an entry without dynamic resolution), whose rate becomes R; the store into the rate state takes R itself, past the table's snap, and so does the parameter apply (`main+0x1605320`, the only other writer). R = 1.0 is the game's own native path; R > 1 turns its upscaler on. `fmov` encodes 1.6875 (27/16), not 1.7: Balanced renders 1707x960 of the 2880x1620 window (1.7 would be 1694x953). 1.5, 1.6875 and 3.0 are rates the game never chooses itself (its table's are snapped to); where the scene's size is computed from the rate was not found (statically only the controller reads +0xc), so a consumer that expects a table rate is the main risk. Also scaled by the rate: the bloom buffer (`BloomBufferBaseScale` x rate, so a fixed share of the output) and two values at `[ctrl+0x40]+0x56c`.
- **Dynamic, as first patched (resolved):** the earlier rows only set the controller's bounds to R and 2.0. Static analysis shows why a stage still started native: the parameter apply wrote R (its row had no condition), but the controller then overrode it. (1) A scene entry without dynamic resolution (+0x29 clear, or the renderer's flag bit 1 off) takes the fixed-rate path, `ldr s8,[x20,#0x2c]`, the entry's own rate, unpatched in dynamic mode; (2) the min bound only stops a step toward sharper (`main+0x38dd60` `fcmp s0,s2; b.ls`: at or below the min it keeps the current rate) and never lifts a rate below it, so a 1.0 held until a frame was over budget; (3) the store snaps its rate down to a table rate (`main+0x38deb8`-`0x38df08`, the largest at or below it), so a non-table R such as 1.5 is stored as 1.375, sharper than chosen. At 1.0 the controller also turns the upscale flag and mip bias off, so MetalFX did not run.
- **Dynamic, now (static analysis):** every path of the controller joins at `main+0x38de2c` (`ldr x9,[x19,#0xf0]`, before the `fcmp s8,s9` that decides whether to store). That word becomes `b main+0x38debc`, into the snap loop, which is dead once `main+0x38deb8` (`cbz w10`) becomes `b main+0x38df0c` (no other branch enters `0x38debc`-`0x38df08`; checked over ±16 KB). There: `fmov s0,#R; fmaxnm s8,s8,s0` (never sharper than R), `fmov s0,#F; fminnm s8,s8,s0` (never softer than the softest; `DM_UPSCALE_SOFTEST`'s two words: without it they stay `add x11,x9,#4` and `csinc w10,w10,wzr,gt`, dead registers here), the replaced `ldr x9,[x19,#0xf0]`, `b main+0x38de30`. `main+0x38dea4` `ldr s0,[x8,#8]` → `fmov s0,s8`, so the store takes the clamped rate (not min with the NDSR ceiling at +8, as the fixed rate does not). The controller's own bounds become 1.0 and 2.0, so it steps through all of its table and the clamp maps each step into [R, F]: from R it can step softer to a table rate or F, and back to R when the frame time allows (a step to sharper below R is clamped to R, which equals the current rate, so nothing is stored and its frame counter is not reset). The step to softer's last resort, `main+0x38e278` (`fmov s2,s4`, the current rate when no table rate is left within its max), returns F, so a softest past the table (Ultra performance) is reached. Both writers of the rate state hold the range: the parameter apply writes R at every parameter read (stage start), and the controller's store is clamped; nothing else writes +0xc (all `ldr x,[x,#0x270]` users scanned: only `main+0x38dea0` and `main+0x1605320` store +0xc; the apply has no direct caller, it is slot 5 of the vtable at `main+0x23c7130`, an agl parameter object's post-read). Rate 1.0 as R: the game's own native path, upscaler and MetalFX off at R, on when softer.
- **Invalid pairs:** a softest sharper than R is raised to R by its own rows (one group per sharpest, `DM_UPSCALE_RATIO=<R>`: label `… raised to …, the sharpest`), and Ultra performance as the softest without a MetalFX upscaler is lowered to Performance. The softest's `when` terms name `DM_UPSCALE_RATIO`, a variable with setting patches of its own, so the host tests what that variable wrote ([Setting patches](../../../docs/reference/cheats.md#setting-patches)): the clamp's words run only inside the sharpest rate's code. The settings window never offers such a pair (`atleast=DM_UPSCALE_RATIO`) and raises a held one with a note.
- **Limits:** between R and F the controller reaches only its own table's rates (1.375, 12/7 seen) and the two bounds; with no table rate between them it switches between R and F. The table's contents (built at run time, `main+0x4a1280`) were not read statically.
- **agl's NDSR at other rates:** one compute variant, `7629d857a0a93833`, drew 1676x943 → 2304x1296 docked (1.375) and 960x540 → 1920x1080 handheld (2.0); each dispatch takes its input and output rectangles from push constants (bank 24, [A game's own upscaler drawn by MetalFX](../../../docs/reference/rendering.md#a-games-own-upscaler-drawn-by-metalfx)), so the ratio is a run-time input, not a network per ratio (2 of the package's 24 variants are in the prewarm list: `7629d857a0a93833`, `5e0110401b4a3d8f`). Its SMAA passes (`main+0x325a80`) have a two-step path (`ndsr::two_step_upscale_input`, a factor at the NDSR object's +0x14) whose trigger was not found. Medium confidence that 1.5 and 1.6875, inside the range the game uses, work; 3.0 was never run, so it is offered only with a MetalFX upscaler: the row's `conflicts=DM_UPSCALER=game:3.0` hides it while the game's own is chosen, and its rows hold only with `DM_UPSCALER=metalfx|metalfx-temporal` (else the host logs that no condition holds and writes nothing). MetalFX's temporal scaler is made for content scales 1 to the device's maximum (3.0 in the HDR capture's log); a frame past it goes to the spatial scaler, and a size MetalFX refuses to the game's own network (`[RED] upscaler: MetalFX spatial scaler … made none`), so with Ultra performance watch for that line.
- **Effects (static analysis):** the render buffer's size ladder (`main+0x424a18`, called at `main+0x423c34`) makes three levels of 0xa18 bytes, each the previous x 0.5; their viewports are the render viewport x 0.5 (`main+0x423c74`) and x 0.25 (`main+0x423d64`). The targets are made each frame at the scene's size (a new serial every frame, the 838x471 targets exactly half of 1676x943), so a target is always its viewport's size. Level 1 holds the half-res targets of the captured frame (F2724, 838x471): the depth / colour downsample (`addf736932b929ae`, `27e0acde07ad5dd7`), SSAO (`a6f04605183d9915`) and its blur (`4d1d373edda7fb86`, `121d99b62fe6824f`), the blob-shadow mask (`b3fa0e4f5ef9ba71`), the refraction scene copy (`e030d1c596051d48`) and the half-res particles (`fea23c5ed52d7a28`, `47380cdf348e48f8`, `b74cd2d174286c7d`) with their upsample (`3f715b6b3de56daf`). `full` makes every level and both viewports the render size, keeping each target its viewport's size (a quarter level at 0.5 would leave a viewport smaller than its target, which the game never does); no level-2 target was in the captured frame.
- **Half-size assumptions (the translated MSL of those 15 shaders and their readers):** all sample with normalized coordinates (no `read()`, no integer `x2` / `>>1` math); every 0.5 or 2.0 literal is an NDC-to-UV conversion, a quad's corner or a smoothstep. The downsample's `gather` covers the pixel and its +x / +y neighbours at full size (exact depth, a slightly conservative tile max). Three texel sizes come from uniforms the CPU fills: SSAO's `c3[3].zw` (its one-texel step and its below-one-texel early-out: if it stays 1/838, 1/471, AO covers only the top-left quarter), the particle upsample's `c3[39]` (half size and its reciprocal: if stale, edges off by up to two pixels) and the blurs' `vp_c3[4].xy` (if stale, a radius twice as large). They most likely come from the viewport the patch changes (about 85 % confidence); a capture of a frame with the setting should show `c3[3].zw` = 1/1676, 1/943 at 1676x943.
- **Shadows:** the per-frame shadow size is the preset x max(scene width / 1920, height / 1080), capped at the preset ([Shadow settings](#shadow-settings)): 0.89 at 1707x960 (about 1820 of 2048), 1.5 at 2880x1620 (the full preset). **Shadow resolution: Full** keeps the preset at any rate.
- **Memory:** the scene's targets are new every frame at the scene size (the captures' serials); four full-size colour / depth targets of 4 bytes a pixel (R11G11B10F scene, RGBA8, RGB10A2, D32F) and the half-res chain (about 20 bytes a pixel at a quarter of the area). At 1676x943 that is about 25 + 8 MB; Window + Balanced (1707x960) about the same; Window + Native (2880x1620, 2.95 times the pixels) about 75 MB, and with effects Full another 90 MB, against the game's fixed graphics heap (about 506 MB). Where the scene's targets are allocated was not found: a heap too small would show as missing passes or a crash on entering a level.
- **The log:** the setting lines (`setting DM_UPSCALE_RATIO=1.5 (Quality (1.5), dynamic: the sharpest): 12 words written: … [DM_UPSCALE_DYNAMIC=1]`, `setting DM_UPSCALE_SOFTEST=1.6875 (Balanced (1.69)): 3 words written: … [DM_UPSCALE_RATIO=1.5 (written)]`, `setting DM_EFFECTS_RES=full (…): 3 words written: …`), then one line with the chain the settings predict (`loader.c` `res_chain_log`, from the profile's `res_chain`): `resolution: docked, output 2880x1620 (single upscale: the window's size); upscale rate 1.5 (sharpest) to 1.6875 (softest), dynamic, start 1.5 (…); scene 1920x1080 to 1707x960; upscaler metalfx-temporal, on at the sharpest; effects …; shadows …` (fixed: `upscale rate 1.6875 fixed, start 1.6875 (…)`; a Native sharpest: `upscaler …, off at the sharpest (rate 1.0: the game turns its upscaler off), on when softer`). The `upscaler: output` line at the first upscale names the sizes drawn.
- **To test:** docked, Window, MetalFX temporal, dynamic Quality → Balanced, effects Full, shadows Full, Locked 60, frame interpolation; check the lines above, that the first upscale draws 1920x1080 → 2880x1620 from the stage's first frame (not 2880x1620 without an upscaler), that a heavy area steps to 1707x960 and back, that ambient occlusion covers the whole picture (not its top-left quarter), soft-particle edges, a level entry, a cutscene and the map for missing passes or a crash. ### Frame rate lock (current, opt-in, not played yet)

`DM_FPS_LOCK` (the Mac settings window's **Frame rate lock**, Advanced settings, Frame rate) is a [setting patch](../README.md#setting-patches) of main v458752 (`e25c90c1…`) in [`setting_patches.tsv`](setting_patches.tsv): `game` (default), `60` (Locked 60), `30` (Locked 30). It stops the game's own 60 ↔ 30 switching ([Open](#open), Frame rate in busy scenes) without the host pinning the present rate.

- **The controller (static analysis):** `main+0x204a18`, called once a frame from `main+0x203718` while VRR is off (`main+0x204640` otherwise), x0 the controller (`[display+0x218]`), x1 the display object. With the frozen flag (+0x58) set or no measure, it keeps its interval (`main+0x204a4c`). Otherwise: v = measure (`[x1+0x128]`, ticks) / tick rate × 60; target = trunc(v + margin) + 1 (margin -0.2 at +0x8, set at `main+0x35efa0`; `main+0x204ab0` `fcvtzs w9,s0`, `main+0x204ab4` `add w10,w9,#1`), clamped to [+0x0, +0x4] (1 to 3). A target above the interval (+0x40) for more than +0xc (2) frames in a row steps up to it; each frame below it counts +0x4c down from +0x10 (6), and at 0 it steps down one interval (+0x44) unless a listener of the list at +0x68 sets the veto byte of the record it is passed (`main+0x204b8c` / `main+0x204b90` `cbnz w8`). It then applies 60 / interval (+0x50, `main+0x204c60` → `vi::SetLayerExtendedSwapInterval`) and the interval (`main+0x204c00`, the `present interval` log line from `main+0x204c20`). The listeners were not identified.
- **The words:** `main+0x204ab0` `1E380009` (`fcvtzs w9,s0`) → `52800009` (`mov w9,#0`, target 1) for Locked 60 or `52800029` (`mov w9,#1`, target 2) for Locked 30; the clamp, the step counters, the frozen path and the swap-interval calls are the game's own. Locked 60 also turns `main+0x204b90` `35FFFC28` (`cbnz w8,#-0x7c`) into `D503201F` (`nop`): the listeners are still called, but cannot hold the game at 30. Checked with `cheat_anchor.py settings` (originals hold, no word the rewriter changed).
- **Game speed:** the game advances a fixed step per frame for its interval, not by the clock: with present snapshots at the host's 30 fps cap it ran 43-65 fps of game time ([Present snapshots](../../../docs/reference/frame-rate.md#present-snapshots-the-games-swapchain-texture-free-at-once)): fast-forward, as the game's frames came faster than its interval. So with Locked 60 a frame that misses 16.7 ms is shown late and the game runs slower for that moment (judder, not a halved rate at real speed); the game's dynamic resolution reads the GPU time against the 60 fps budget and lowers the scene size first. Medium-high confidence: from behaviour, the step's reader was not found in the code.
- **Why it helps on a Mac:** in the logs of 2026-11-03 (M5 Pro) the GPU time of the same scene rose about threefold at interval 2 (`hdrcap` session: 3.9-4.3 ms per 1,000 draws at 30 fps, 1.1-1.4 at 60; `prev_session`: 13.7 → 22 ms within 10 frames of the step up, then 30 fps for 13,400 frames), and the CPU moved to slower cores and clocks: the clocks follow the longer interval, the measure stays above 1.2 vsyncs, and the game never steps back down. Pausing breaks the loop (issue #932).
- **To test:** Locked 60 in a heavy area (much terrain destruction): the log must show `setting DM_FPS_LOCK=60 (Locked 60): 2 words written` and no `present interval 1 → 2` line after the first frames; check that movement and timers keep real speed while the frame rate holds, and how often frames run late (`on-screen … dropped`). Locked 30: one `1 → 2` change, then none.

## Boot (Mac)

Each step below stopped the boot before its fix:

1. `sdk: no SDK version string`: the version reads `nnSdk-Generic_20_5_19` (`loader.c` `dm_sdk_major` skips the variant name).
2. `GetInfo` 0x21, a Switch 2 info type: the kernel's page size. `nn::ro::ProtectRelro` takes value − 1 as the RELRO alignment mask; 0 aborted (`hle_svc.c` answers 0x1000). Type 28 is Horizon's AliasRegionExtraSize (0, named with 25–27 so that Switch 1 games print no new red line); 29–32 are the Switch 2's remote region: `nnosInitialize` builds `nn::os::detail::RemoteRegionManager`'s address space allocator over [type 29, type 29 + type 30), and `nn::os::GetRemoteMemoryUsage` returns types 31 and 32. Only the GPU driver's boot maps into it (`nv::InitializeGraphics` → `nn::gs::sdk::BootGraphicsSystem` → `BootWithRemoteMemory`), and the host replaces `nv::InitializeGraphics` (the overload with a pool, the one the game calls), so all four are 0: no remote region.
3. NVN2 reports API 231: the game requires major 231, minor ≥ 30 (`main+0x5c61a4`) and creates no graphics system otherwise (null read in its frame loop). `dm_sdk_ounce` (the sdk's `spec: Ounce`) selects 231.30 (`hle_nvn.c`).
4. 197 NVN2 entry points (ray tracing, mesh shaders, DLSS, device commands, HDR window metadata, a ProgramBuilder) were unknown names, so lookups returned null; they are in `names.txt` now, the unimplemented ones going to the red stub. Implemented: the ProgramBuilder (`nvnProgramInitializeFromBuilder` = Initialize + SetShaders), `QueueBuilderSetPrimaryQueue`, `CommandBufferSetRecordingMode` / `SetGeometryProcessingMode` / `SetComputeOverlapMode`.
5. Switch 2 SDK calls through services the host does not serve: `hid::InitializeJcms` and the Joy-Con mouse sensor (`hle_hid.c`), `oe::GetCurrentGraphicsScale` (`hle_oe.c`), `audio::IsDeviceOutputVolumeAutoTuneModeEnabled` (`hle_audren.c`), `streamplay` (GameShare, `hle_misc.c`), `vi` HDR / VRR / extended swap interval (`dm/gfx/hle_vi.c`).
6. `nv::InitCheck` (from `main+0xe19d04`, the start of a video decoder, after the first punch) tested the SDK's own flag, which `nv::InitializeGraphics` sets and the host's version of it does not: `hle_nv.c` answers it from the host's record. The same function then starts a video decoder: the Switch 2's `nn::codec` video API and sync point events, served on the host ([`nn::codec` video decoders taken over](../../../docs/reference/movies.md#nncodec-video-decoders-taken-over)).
